<objective>
Ship a new POST endpoint at `/api/rsvp/submit` that accepts a household_id plus an array of per-guest submissions and writes them atomically to `public.rsvps` via a single batched upsert keyed on `guest_id`. Re-submitting the same payload updates in place (no duplicates) — the upsert + the partial unique index `rsvps_guest_id_uniq` from Plan 04-01 give natural idempotency without an Idempotency-Key header (CONTEXT Claude's Discretion). The route also defends against cross-household guest_id spoofing with a pre-flight authz SELECT.

Purpose: This is the write-side half of the v0.2 API contract. Phase 6's group form submits to this endpoint; Phase 6's "edit response" affordance re-submits via this same endpoint relying on upsert semantics (GROUP-03). The meal_choice enum is validated at the app layer per D-14 / CONTEXT Claude's Discretion so Phase 6 can swap the placeholder values (`["chicken","fish","vegetarian"]`) with the real menu in a one-line change when MEAL-02 lands.

Output:
- `app/(main)/api/rsvp/submit/route.ts` (new) — Next.js 16 Route Handler exporting `POST(request: NextRequest)`. Flow: input validation (uuid + enum + non-empty array) → pre-flight authz (guest_ids ⊆ household members) → batched upsert via `onConflict: "guest_id"` → sanitized success/error response.

Verification is curl-based smoke against `npm run dev` against the live Supabase + Plan 04-01 dev seed. The two-member Tyler+Emily household is the primary fixture for the multi-row + idempotency tests; the single-member Sarah Else household covers the N=1 boundary.

This plan runs in Wave 2 in parallel with Plan 04-02 — both depend only on 04-01's schema, neither shares files with the other.
</objective>
